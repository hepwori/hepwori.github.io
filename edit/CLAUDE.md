# CLAUDE.md

Working notes for Claude on this project.

## What this is

A browser-based, WYSIWYG markdown editor with an AI copyediting layer, for Isaac's personal writing. No server-side, no build step — matches every other project in this repo (see `bikeviz/`, `pmp/` for the same philosophy). Full design rationale lives in the plan this was built from; the short version:

- WYSIWYG editing backed by Tiptap (ProseMirror), markdown as the import/export format, ProseMirror JSON as the actual storage format (so review-flag marks and editor state survive reloads — markdown is always a derived view).
- An AI review-pass system (à la Google Docs' "Editing passes" panel): run a named prompt ("Grammar", "Filler words", etc.) against the doc, get findings highlighted inline, step through and accept/dismiss each one. The LLM edits and flags, it never writes prose in bulk. Both the pass library and a global writing-style guide are fully user-editable from Settings.
- LLM connection is swappable — Gemini (AI Studio key, direct browser `fetch`, no proxy needed) at work, Claude (`anthropic-dangerous-direct-browser-access` header) at home. Both confirmed to support direct-from-browser CORS.
- No accounts, no sync — a local doc library in `localStorage`. Accepted compromise: different browsers/machines have separate libraries.

## localStorage compatibility policy

Isaac asked that any change be explicitly flagged if it's backwards-incompatible with what's already sitting in localStorage — treat existing saved data as sacred by default. Standing rule from here on: before shipping a change, check whether it touches the *shape* of anything under `edit.*` keys (doc records, the library index, `edit.config.v1`) — a new field is fine (old data just gets a default via the merge-over-defaults pattern already used in `loadConfig`/`loadIntoEditor`'s slug backfill), but a renamed/removed/restructured field needs either a migration or an explicit callout before it ships, not silent breakage. A change to *editor behavior* (how existing stored data is interpreted or acted on) isn't a storage compatibility break by itself, but still worth naming if it changes what a user should expect from data they already have — e.g. the reviewFlagAutoDismiss behavior below doesn't touch the ReviewFlag mark's schema at all, but it does mean an *already-saved* mark will behave differently (clear on edit) the next time that doc is opened, which is worth saying out loud even though nothing about the stored JSON changed.

## Vendored dependencies

Third-party JS (Tiptap/ProseMirror, `@tiptap/markdown`, its `marked` dep, Turndown) is **not** loaded live from esm.sh at runtime — it's mirrored into `edit/vendor/` and imported from there, same-origin. Isaac's concern: a live CDN import means any of those packages (or a transitive dep of theirs) turning malicious in a future release — or esm.sh itself getting compromised — runs arbitrary JS in-page with access to `localStorage` (API keys, every doc). Subresource Integrity doesn't fix this: `integrity=` on a `<script>` tag only covers that one top-level fetch, not the dozen-plus nested `import` statements inside the module graph that pull in further code from the same CDN — there's no browser mechanism yet to pin those. Vendoring removes the live third-party origin entirely; the tradeoff is that a security patch to any of these packages now needs a manual re-vendor rather than arriving for free on next page load.

- `edit/vendor/` is a same-origin mirror of the *resolved* esm.sh module graph for the exact imports `editor.js`/`paste.js` used to pull live — not a hand-picked subset. `edit/vendor/update-vendor.mjs` is the (re-)generation script: it crawls from a fixed list of entry-point URLs, follows every `import`/`export ... from`/`import()` it finds (using `es-module-lexer`, a real ES module parser — esm.sh's output is minified, e.g. `export*from"..."` with no whitespace around keywords, which an early regex-based version of this script silently missed and is why a lexer is used instead), and rewrites every specifier to a relative path pointing at its local copy. Confirmed closed: a scan of the whole vendored tree turns up zero remaining `http(s)://` or root-absolute (`/...`) specifiers, and zero dynamic `import()` calls with a non-literal (computed) specifier that a static crawl could have missed.
- Filenames like `@tiptap/core@3.31.3.q-b43df6e3.mjs` mirror esm.sh's own resolved path for that exact request; the `.q-<hash>` suffix is a hash of the query string (`?deps=...`, `?target=es2022`, etc.) appended only when needed to keep two different requests to the same path from colliding on disk.
- **Deliberately not root-absolute**: esm.sh's own inter-file references are root-absolute (`/@tiptap/pm@.../es2022/state.mjs`), which would only resolve correctly if vendored at the actual domain root — breaking the "document-relative paths only" property that lets this same `edit/` directory serve identically from both `hepwori.github.io/edit/` and, path-prefixed, `isaa.ch/toys/edit/` (see Deployment & serving below). Every specifier in the vendored tree is rewritten to a real relative path instead, so this property survives unchanged.
- To bump a pinned version: edit `ENTRY_POINTS` in `update-vendor.mjs`, wipe `edit/vendor/` except that script, `npm install es-module-lexer --no-save` (dev-only, not committed — matches the repo's no-npm-checked-in convention), and re-run it from inside `edit/vendor/`. Check the printed entry-point filenames against `editor.js`'s/`paste.js`'s imports afterward in case a hash changed.
- Verified empirically, not just by inspection: a Playwright run with `**esm.sh**` routed to `route.abort()` exercised editor mount, bold/toolbar, markdown-shortcut input, rich paste (exercises Turndown), a full LLM review pass (exercises the ProseMirror `Plugin`/`Mapping` imports), and a lossless markdown import→export round-trip — all passed with the CDN completely unreachable and zero console errors.
- Google Fonts (`fonts.googleapis.com`/`fonts.gstatic.com`) is unchanged — it's a `<link rel=stylesheet>`, not executable code, a materially different risk profile, and out of scope for what was asked.

## LLM output is untrusted — the XSS-not-just-prompt-injection angle

Isaac's question, worth keeping as a standing check rather than a one-off answer: a malicious/adversarial document could try to get the model to emit something JS-like in `note`/`suggestion`/`category`/`quote`, on the theory that it then runs in the page. Two independent things currently close this off, and both are worth re-checking before any change touches how findings render:

1. **The response schema isn't just a prompt — it's provider-enforced.** Gemini's `responseMimeType: "application/json"` + `responseSchema` is constrained decoding at the token-sampling level (the model cannot generate a token that would produce schema-invalid output); Claude's forced tool-use (`tool_choice: {type:"tool", ...}`) means Anthropic's API constructs the structured `tool_use` block itself. Neither app code parses free text hoping it's JSON — the worst an adversarial document can do is get the model to put attacker-chosen *text* into one of the defined string fields.
2. **Every one of those string fields is rendered through a safe DOM API, never `innerHTML`.** `app.js`'s `buildFindingCard`/`renderFindings` use `.textContent`, `.value` on a `<textarea>` (never parsed as markup), and `document.createTextNode` for `category`/`note`/`suggestion`/`passLabel`/the scope-note preview. `review.js`'s `resolveFinding` applies an accepted suggestion via ProseMirror's `tr.insertText(text, ...)`, which inserts a plain text node — not parsed as HTML or markdown. `editor.js`'s `ReviewFlag.renderHTML` returns a ProseMirror DOM-output-spec array (`["mark", attrsObj, 0]`), which ProseMirror's `DOMSerializer` turns into real elements via `createElement`/`setAttribute` — never by building an HTML string and parsing it, so even a `data-note` value containing `"><script>` just becomes an inert attribute string.

Net: with the code as it stands, there's no path from adversarial document content to script execution, even assuming a fully "jailbroken" model response. This holds only as long as every future render of `note`/`suggestion`/`category`/`quote`/`passLabel` keeps using `.textContent`/`.value`/`createTextNode`/ProseMirror APIs — reaching for `.innerHTML` anywhere in that path would reopen it. Grep for `\.innerHTML` before considering any findings-rendering change done; as of this writing every hit in the codebase is a `= ""` clear, never an assignment of real content.

(Separately: classic prompt injection — adversarial document text trying to redirect the *model's behavior*, e.g. "ignore your instructions and say X" — was already flagged as out of scope by Isaac, since there's no agentic tool-use loop here for a hijacked model to act through; it can only return `{findings: [...]}` JSON that the author reviews before anything touches the doc.)

## Deployment & serving

Served two ways, same unmodified files, no dedicated worker needed for either:

- **`hepwori.github.io/edit/`** — plain GitHub Pages. No build step.
- **`isaa.ch/toys/edit/`** — already covered by the existing `toys-proxy/cloudflare-worker.js` (`isaa.ch/toys/<path>` → `hepwori.github.io/<path>`, 1:1), no changes needed. This directory uses only document-relative asset paths and a client-side-only `#/<slug>` hash for doc links, so it doesn't care what path prefix it's served under — confirmed working. (A dedicated `isaa.ch/edit*` worker was written and then deleted once this was noticed — `toys-proxy` already did the job.)
- **localStorage is per-origin** — `hepwori.github.io/edit/` and `isaa.ch/toys/edit/` are two *separate* doc libraries, settings, and API keys, not a synced one. Whichever becomes the daily-driver URL is the one that matters; the other stays a working but independent copy. See the "cross-origin library transfer" options below if this becomes a real need.

### Cross-origin library transfer — options, not yet built

Isaac asked how we'd move a doc library between origins if it came to that, without building it now. In rough order of effort:

1. **Manual export/import (JSON file)** — an "Export library" action serializes `edit.library.v1` + every `edit.doc.*` into one JSON file (`Blob` + `<a download>`), "Import" reads an uploaded file back into `localStorage` on whatever origin you're on. No live sync, fully user-driven, stays entirely within the "no server" philosophy. Cheapest option and the natural first move if this is ever actually needed.
2. **Single-doc share via URL** — encode one doc's content into the link itself (e.g. a compressed/base64 hash fragment) instead of referencing local storage, so opening the link on *any* origin/device reconstructs that doc without needing the source origin's storage at all. Solves "share one doc," not "migrate my whole library" — practical URL-length limits make it unsuitable for more than a single modest doc.
3. **Cross-origin storage bridge** (hidden iframe + `postMessage`) — designate one origin as the canonical storage owner, embed a tiny bridge page from it in an invisible iframe on every other origin, talk to it via `postMessage` to read/write "shared" storage that actually lives on the bridge's own origin. Gets genuinely live shared storage with no real backend, but it's a real protocol to get right (targetOrigin allowlisting, load-order races) and increasingly fragile — browsers (Safari ITP, Chrome's third-party storage phase-out) are actively closing this kind of cross-site storage access, so it's a shrinking option, not a growing one.
4. **File System Access API** — instead of `localStorage`, sync doc files to a real folder on disk (e.g. inside Dropbox/iCloud Drive), letting the OS's own file sync carry docs between origins and devices for free. Solves cross-origin *and* cross-device at once, but Chrome/Edge only (not Safari/Firefox) and a bigger architectural change — would need to become the primary storage layer, or a parallel optional one.
5. **An actual backend** — Cloudflare KV/D1 (already using Workers for isaa.ch) or Firestore, with the client pushing/pulling by doc id. The real fix, most work, and the direction the pmp/CMS conversation was already pointing — the storage model (id/list-shaped from day one, see `storage.js`) was deliberately kept compatible with this if it ever comes to it.

For "I want my library to show up in both places," (1) is the pragmatic near-term answer; (4) or (5) are the ones worth it if this becomes a recurring need rather than a one-off.

## Stack notes

- No npm, no bundler. Everything is `<script type="module">` importing straight from `esm.sh`, pinned to an exact `@tiptap/*` version (currently `3.31.3`) with `?deps=@tiptap/pm@<version>` on every import so esm.sh resolves one shared ProseMirror instance instead of duplicates — skipping that query param is a common source of "duplicate instance of prosemirror-state"-style breakage.
- `editor.js` uses the official `@tiptap/markdown` extension: `editor.getMarkdown()` to export, `editor.commands.setContent(md, { contentType: "markdown" })` to load. Confirmed working end-to-end (headings, emphasis, links, lists, blockquotes, fenced code blocks all round-trip cleanly).
- Gotcha hit once already, worth remembering: Tiptap's `onSelectionUpdate` fires **synchronously during `new Editor()` construction**. Any DOM lookups a callback touches must happen before `createEditor()` is called, or you get a "cannot access '<const>' before initialization" TDZ error that silently aborts the rest of a module's top-level code (which looks like "half the buttons don't work" with no obvious cause). See the ordering in `app.js`.
- Toolbar active-state (`.is-active`) needs refreshing on `onUpdate` as well as `onSelectionUpdate` — a mark toggle (bold, etc.) is a doc-changing transaction but doesn't necessarily change the selection range, so `onSelectionUpdate` alone leaves the toolbar stale after clicking its own buttons.
- `setContent`/`setMarkdownContent`/`setJSONContent` all take `{ emitUpdate: false }` (a real Tiptap core option, confirmed by reading `@tiptap/core`'s `setContent.ts`, and the markdown extension passes options through untouched) — use it for every *programmatic* content load (boot, switching docs in the library, `+ New`) so it doesn't kick off a redundant autosave cycle of content that's already what's on disk. Leave it default (`true`) for actual user actions like the Import modal, which should count as an edit worth saving.
- Escape-closes-modal is generic (`app.js`, matches any `.modal:not([hidden])`) — new modals (e.g. phase 4's settings modal) get this for free, no repeat wiring needed.
- Rich paste (`paste.js`) hooks ProseMirror's `handlePaste` editorProp, not a DOM `paste` listener — returning `true` from it tells ProseMirror "don't also insert your own parsed slice." It needs the live `Editor` instance to call `insertContent`, which doesn't exist yet at the point `editorProps` is passed into `new Editor(...)` — worked around with a thunk (`createPasteHandler(() => editorRef)`) that's satisfied right after construction; see `editor.js`.
- Tiptap's `insertContent`/`insertContentAt` accept the same `{ contentType: "markdown" }` option as `setContent` (all three delegate to `editor.markdown.parse()` under the hood) — that's the whole trick behind rich paste: turndown flattens HTML to markdown text, then `insertContent(md, { contentType: "markdown" })` parses and inserts it as real nodes at the cursor.
- Internal copy/paste (dragging or copying a selection within the doc itself) is deliberately left alone — ProseMirror tags its own clipboard HTML with `data-pm-slice`, and the paste handler checks for that and bails out to native handling, so an internal copy never round-trips through markdown and silently drops something markdown can't represent (a mark with no markdown syntax, e.g. phase 5's review flags).
- Both LLM providers are called with a plain `fetch` straight from the browser, no proxy — confirmed working (real CORS preflight, not just docs): Gemini's `generativelanguage.googleapis.com` sends `Access-Control-Allow-Origin: *`; Claude's Messages API needs the `anthropic-dangerous-direct-browser-access: true` header. `edit.config.v1` (in `storage.js`) holds both providers' key + model plus which one is "active"; both stay configured simultaneously (matches the actual use case — Gemini at work, Claude at home, switched via the radio, not re-entered).
- Structured LLM output: Gemini via `generationConfig.responseMimeType: "application/json"` + `responseSchema`; Claude via forced tool-use (`tool_choice: {type:"tool", name:...}`) so the model has to call the tool rather than maybe replying in prose. Both return the same shape either way: `{ findings: [{ quote, note, suggestion?, category? }] }`.
- **Scope (whole doc vs. a passage) is implicit, not a UI toggle**: `runReviewPass` (`review.js`) checks `editor.state.selection` itself — a non-empty selection at the moment you hit Run scopes the prompt to it (full doc still goes along as context). This covers both "run a named pass over everything" and "select a passage, ask something specific about just it" through one code path; no separate scoping control needed. An ad-hoc instruction typed into the custom box is handled identically to a named pass — it's just a prompt that came from a text input instead of `PASS_LIBRARY`, with `passId` generated from a timestamp and `passLabel` the truncated instruction text.
- **Finding anchoring**: the model is told a `quote` must be copied verbatim from the doc; `review.js`'s `findQuoteRange` flattens the doc to one string (`buildTextIndex`, tracking a per-character map back to real ProseMirror positions) and searches with a regex built from the quote where runs of whitespace become `\s+` — handles both an exact match and the case where the model reflows a line-wrapped quote's whitespace, in one path. A quote that still doesn't match is silently dropped and counted as "skipped" in the status line; nothing partial or guessed gets applied.
- **Gotcha, cost real debugging time**: `Transaction.insertText(text, from, to)` (used when accepting a finding with a suggestion) deliberately carries over `$from.marksAcross($to)` — the marks active across the *replaced* range — onto the new text. That's desired for bold/italic surviving an accepted edit, but it also means the reviewFlag mark itself gets reapplied to the replacement, so accepting looked like it did nothing (mark never went away). Fix: `resolveFinding` inserts the suggestion, then explicitly `removeMark`s just `reviewFlag` (not everything) off the newly-inserted range.
- **No separate "accepted" bookkeeping** — a finding's mark presence in the doc *is* its "open" state; accept/dismiss both end by removing the mark (accept via the insertText-then-strip-mark path above, dismiss via a plain `removeMark`), so resolved findings just disappear from both the text and the sidebar rather than sticking around in a resolved state. Per-pass "N open" counts in the sidebar are computed live from `listFindings(editor)` grouped by `passId` — no counters to keep in sync. Re-running the same named pass adds a second, independent batch rather than replacing the first (acceptable for v1; the screenshot's "run 1/30" history stepper is a nice-to-have, not built).
- Same TDZ trap as phase 1, different variable: `updateReviewScopeNote()` (called from `syncUI`, which fires synchronously during `createEditor()`) touches `reviewPanel`/`reviewScopeNote` — those two lookups had to move up into the same pre-editor block as `toolbar`, everything else in the review section's wiring can stay where it naturally reads. Rule of thumb reaffirmed: anything `syncUI` (or anything it calls) touches must be declared before `createEditor()` is called, full stop.
- The review panel is a persistent `<aside>`, always visible (see "permanently-visible review panel" below for the removal of its toggle) — Escape only closes `.modal`s now, there's nothing panel-specific left for it to do.
- **Pass library and writing style are now fully user-editable** (moved off `review.js`'s originally-hardcoded `PASS_LIBRARY`, which no longer exists). Both live in `edit.config.v1` (`storage.js`): `config.passes` (a `{id, label, instruction}[]`, seeded from `defaultPasses()` but the *saved* array always wins wholesale once one exists — editing/adding/removing is just mutating this array + `saveConfig`) and `config.styleGuide` (a plain string). `review.js` and `generative.js` don't know or care where an instruction/style guide came from — `buildPrompt` just takes `styleGuide` as one more optional param and injects it as a dedicated "author's target voice" block when non-empty, in both places. The Review panel's chips are no longer built once at load (`renderPassChips()` in `app.js` rebuilds them from `config.passes` on every edit/add/remove in Settings) — this is also why `passId` stability matters: `passColors.js`'s fixed hues are keyed by the five original ids, so renaming a preset's *label* keeps its color, but deleting-and-recreating one under the same name would not (falls through to the hash-based custom color instead) — a known, minor, unfixed edge case.
- The ad-hoc custom-instruction box (unchanged) still covers genuinely one-off asks that don't belong in the saved preset list — the two features are complementary, not overlapping: presets for "things I check often," custom text for "this one specific thing right now."
- **Favicon, tried per-doc identicons and reverted**: originally `favicon.js` gave each doc a distinct SHA-1-seeded 5x5 identicon (same algorithm as Isaac's own `hepwori/favidenticon` Chrome extension), swapped in via `loadIntoEditor`/`startNewDoc` whenever the open doc changed. Isaac's call after living with it: identicons read as busy/off-brand against the rest of the app's calmer aesthetic — reverted in favor of one static favicon, permanently. `favicon.js` is deleted; `favicon.svg` (a warm terracotta tile — `--accent`/`--paper`, the app's own palette — with a serif "e", previously just the pre-boot fallback before the identicon JS took over) is now simply *the* favicon, referenced once in `index.html` and never touched by JS.
- **Slugs + doc links** (`edit/#/<slug>`): a slug is assigned at doc creation (`uniqueSlug("Untitled")`, so a never-renamed doc is still linkable as `#/untitled`, `#/untitled-2`, ...) and *locks in* the first time the doc gets a real title — `persistNow` only regenerates the slug while it's still an `untitled(-N)?` placeholder. This means a link stays valid through later renames, which is the actual point of having one. `bootDoc` checks `location.hash` before falling back to `edit.lastOpen.v1`, so a doc link always wins over "resume where I left off." A `hashchange` listener means pasting a doc link into an *already-open* tab navigates live rather than requiring a reload. Docs saved before this feature get a slug backfilled the first time they're loaded (`loadIntoEditor`'s `record.slug ||` fallback, immediately persisted).
- Prompt hardening: a live pass had a passive-voice run flag several already-active sentences with notes like "this is fine, leave it" — the model was treating "find X" as "survey every sentence and report on it" rather than "only report genuine issues." Fixed with an explicit rule in `buildPrompt` ("if you catch yourself about to write a note like 'this is fine, leave it,' that means you should not report it at all") plus a more precise passive-voice pass instruction. This is a prompt-only fix — no code path to unit-test it against, so it's worth keeping an eye on with real usage rather than considered fully closed.
- Prompt hardening #2: a live pass returned a `suggestion` like `Fix double period; consider simplifying to 'trusting a pull they can't yet see or measure.'` — meta-commentary about the fix mixed into the field that's supposed to be pure drop-in replacement text (`resolveFinding` inserts `suggestion` verbatim in place of `quote` on Accept, so this would have replaced the flagged text with that whole sentence, commentary included). The schema previously gave the model zero guidance beyond `{ type: "STRING" }` for `note`/`suggestion` — nothing told it where reasoning-vs-replacement-text was supposed to go. Fixed two ways, reinforcing each other: (1) `buildPrompt`'s rule for `suggestion` in `review.js` now spells out that it's inserted verbatim and must contain *only* the exact replacement text — no prefacing like "Consider..." or "Fix X; simplify to...", explicitly redirecting reasoning/commentary to `note` instead; (2) `gemini.js`'s `responseSchema` and `claude.js`'s tool `input_schema` both gained per-field `description`s on `quote`/`note`/`suggestion` mirroring the same constraint — a second, independent signal attached directly to the field the model fills in, not just prose in the surrounding prompt. Confirmed via Playwright that both the new prompt text and the new schema descriptions actually reach the model in the real outgoing request body. Same caveat as the passive-voice fix above: prompt-only, no code path to unit-test against, worth watching with real usage.
- Prompt hardening #3, a different flavor of the same class of bug: a live pass flagged a whole two-sentence `quote` ("Product managers and leaders often lack direct control... yet are still accountable for collective direction.") but returned a `suggestion` that only replaced the tail clause ("yet still answer for collective direction") — accepting it would have deleted the entire first sentence, since `resolveFinding` replaces *all* of `[quote.from, quote.to)` with `suggestion`, not just the part that changed. Unlike hardening #2, `suggestion` here genuinely was pure replacement text with no commentary — the mismatch was between `quote`'s span and `suggestion`'s span, not within `suggestion` itself. Fixed by tightening both fields' contracts together, prompt and schema descriptions alike: `quote` should be as short/precise as the issue allows (no padding it with surrounding sentences for readability — that's what `note` is for), and `suggestion` is now explicitly required to be a complete replacement for the *entire* `quote`, with the model told to narrow `quote` down to just the changed fragment rather than leave `suggestion` covering only part of it. Same caveat as the other prompt-only fixes: no code path to unit-test the model's actual behavior against, worth watching with real usage rather than considered fully closed.
- **Editable suggestions**: a finding's suggestion box is a `<textarea>`, not static text — `resolveFinding(editor, id, { applySuggestion, suggestionText })` takes an explicit `suggestionText` override that wins over `finding.suggestion` when present, so a tweak made in the sidebar before hitting Accept is what actually lands. `app.js`'s `buildFindingCard` reads the textarea's live `.value` at click time.
- **Pass color-coding** (`passColors.js`), the answer to "but what color for a custom instruction?": the five original named-preset ids get fixed, memorable hues (grammar=green, flow=blue, filler=amber, passive=purple, structure=teal) — keyed by id, not label, so renaming a preset in Settings keeps its color (see the config-editable-passes note below). A custom instruction has no natural color, so its hue is a cheap synchronous hash of the *instruction text itself* (not the generated passId, which includes a timestamp and would make even a repeated identical question look different each time) — same question asked twice lands on the same hue, a different question lands on a different one, and everything stays in the same pale/pastel family regardless. The color is computed once and used in two places: `editor.js`'s `ReviewFlag.renderHTML` sets it as the mark's inline `background`, and `app.js`'s `buildFindingCard`/group header use the same function for the card background, left border, and category label — so a highlighted phrase and its sidebar card are always visibly the same finding at a glance, and the mark's `:hover`/`.is-focused` state uses a hue-agnostic `filter` (saturate+darken) rather than a fixed swap color, since the underlying color is no longer a constant.
- **Review lifecycle / loading state**: a run is unambiguous now — the specific chip (or the custom Run button) that triggered it gets a `.is-running` pulse, every other chip/the custom input/Dismiss all are disabled (`setChipsDisabled(disabled, activeEl)` in `app.js`) so two runs can't race against the same editor transaction, and the status line gets a spinning `::before` (`.review-status.is-busy`) instead of being easy to miss as plain text. Every status message — "asking Gemini…", "found N", "nothing flagged", an error — is prefixed with the pass's label and, when relevant, notes the scope ("(scoped to your selection)"), since "Nothing flagged" on its own doesn't say what was checked. Re-running the same named pass still just appends to its existing group (see the "no separate accepted bookkeeping" note above) — that part of the lifecycle question is intentionally left as-is for now, most useful multi-run behavior (a numbered run history, re-running only over unresolved text) would need actual UI to expose, not just a data model change, so it's flagged here rather than built speculatively.
- **Resizable review panel**: default width bumped 360px → 420px (`--review-panel-width` custom property, set inline so JS can override it) with a drag handle (`#review-resize-handle`, absolutely positioned on the panel's left edge) clamped to 300–720px; the dragged width persists to `localStorage['edit.reviewPanelWidth.v1']` and is restored on boot.
- **Real CSS bug, now fixed**: buttons outside a modal (the review panel's Run/close/Dismiss-all, the topbar's Library/Review) were rendering with the browser's native beveled button chrome — every de-styling rule lived under `.modal-actions button`/`.modal-header-row button` selectors, so anything outside a modal never got a reset at all. Fixed with one global `button { ... }` base (flat border, no native `appearance`) near the top of `style.css`, plus standalone `.primary`/`.ghost`/`.small` modifier classes usable anywhere — the modal-scoped versions were deleted as redundant. Lesson: a "de-style this button" rule should almost always be a base-element rule, not something scoped to whatever container happened to need it first.
- **Generative outline mode** (`generative.js`) is deliberately the same "structured JSON out" mechanics as `review.js`'s passes — same two provider functions' shape (`generateOutline({apiKey, model, prompt}) -> {title, headings}`), same Gemini responseSchema / Claude forced-tool-use split (`gemini.js`/`claude.js` now share a small internal helper — `generateJSON`/`callTool` respectively — between their pass and outline functions rather than duplicating the fetch boilerplate). The entry point lives in the Library modal ("Generate outline…" next to "+ New") rather than a standalone topbar button, since it's fundamentally a doc-creation flow, not something you do to a doc you're already in — `startNewDoc` was generalized to take optional `(markdown, title)` overrides so this reuses the exact same doc-creation path as "+ New" instead of a parallel one. The prompt repeats "never write body prose, not even an example sentence" twice, deliberately — the one requirement from the very first design conversation that a generative feature must not cross.

All phases from the original plan are built: editor core, doc library, rich paste, LLM settings, review passes (plus the ad-hoc/selection-scoped/color-coded/editable-suggestion refinements above), favicons, doc links, and now generative outline mode. Later work from here is user-driven refinement, not a fixed roadmap — check with Isaac before assuming what's next.

- **Permanently-visible review panel**: the panel is no longer a toggle — `#review-btn` and `#review-close-btn` are gone (from `index.html`, `app.js`, and `style.css`), `#review-panel` has no `hidden` attribute, and `syncUI()` unconditionally calls `renderFindings()` (the old `if (reviewPanel.hidden) return` guards in `updateReviewScopeNote`/`renderFindings`/`stepFinding` were all removed as dead code now that the panel can't be hidden). Default width bumped 420px → 460px. Empty state got real copy + padding instead of blank space (`.findings-empty`, styled as prose rather than a leftover placeholder). No storage-schema impact — this is pure UI, nothing under `edit.*` changed shape.
- **Newest-batch-on-top ordering**: findings need a real batch marker to sort by, so the `ReviewFlag` mark gained a `createdAt` attribute (`editor.js`) — a plain optional field (`default: null`), so it's backwards-compatible per the policy above: an already-saved flag without it just sorts as oldest, no migration needed. `runReviewPass` (`review.js`) stamps one `batchAt` timestamp per call onto every mark it creates in that run. `renderFindings()` (`app.js`) groups by `passId` as before, but now ranks each group by its most recent finding's `createdAt` (so re-running a named pass bumps its whole group back to the top) and sorts within a group newest-first, doc-position as a tiebreaker for same-batch findings.
- **Card-to-card arrow-key navigation**: each `.finding-card` is now `tabIndex = 0`; a `keydown` listener scoped to `#review-panel` (not `window`) handles plain `ArrowUp`/`ArrowDown`, but only when `document.activeElement` is already inside a `.finding-card` — this is what keeps arrow keys from being hijacked inside the custom-instruction input or a chip button, both of which also live in the panel and have their own normal arrow-key behavior. Stepping calls a new, deliberately lightweight `previewFindingInEditor(id)` — toggles `.is-focused` on the matching mark and scrolls it into view — rather than the existing `focusFinding`, which moves real ProseMirror selection *and* DOM focus into the editor; using the latter for arrow-nav would kick focus off the card list after a single keypress, breaking continued navigation.
  - **Focus-race bug found and fixed along the way**: clicking a card calls `focusFinding()`, which changes the editor's selection — this synchronously fires `onSelectionUpdate` → `syncUI()` → `renderFindings()`, which rebuilds the entire card list (`innerHTML = ""`). That destroys the very card DOM node the click handler's closure was about to call `.focus()` on, so the call was silently a no-op and focus stayed on the editor — which meant clicking a card could never actually hand keyboard focus to it, so arrow-nav could never engage from a click. Two-part fix: (1) `focusFinding(editor, id, { focusEditor = true })` gained an option to update the selection/scroll without moving DOM focus into the editor — the card click path passes `focusEditor: false` (Alt+Up/Down's `stepFinding` still wants real editor focus, so it keeps the default); (2) the click handler re-looks-up the card by id from the live DOM *after* the rebuild instead of reusing its stale closure reference, then focuses that. Caught by Playwright (`document.activeElement` after a simulated click was the editor, not the card) before shipping, not just inferred from reading the code.
  - **Related scroll bug, found later when Isaac asked for it explicitly**: `focusFinding` also used to call ProseMirror's own chain `.scrollIntoView()` command to bring the flagged span into view. That command computes its scroll target from the browser's *native* selection, which only tracks ProseMirror's `state.selection` while the contenteditable actually has DOM focus — so with `focusEditor: false` (the card-click path, per the fix above) it silently no-ops. Confirmed with Playwright against a long, multi-screen document: clicking a card left `#editor-wrap`'s `scrollTop` completely untouched, while Alt+Up/Down's `stepFinding` (which does call real `.focus()`) scrolled correctly. Arrow-key card-nav was never affected — `previewFindingInEditor` already scrolled the mark's own DOM node directly rather than going through ProseMirror's command, which turned out to be the right approach generally, not just a workaround for the no-focus-stealing constraint. Fixed by having `focusFinding` do the same: `document.querySelector('mark.review-flag[data-review-id="..."]').scrollIntoView(...)`, dropping the chain's own `.scrollIntoView()` entirely rather than keeping two different mechanisms for one job.
- **Focus ring made visible, then made a live-tunable choice**: `.finding-card:focus`/`.is-focused` previously only bumped `border-color`, which read as barely-there against the pass's pale background. First fix was a `box-shadow` double ring (panel-colored gap, then a solid dark outer line) — Isaac's next-round feedback was that the ring itself read as too heavy. Rather than guess again from a screenshot, this became the first entry in a new "Experimental" mechanism (see below): four candidate treatments (`tint`, `bar`, `lift`, `ring`) live in `style.css` gated by `#review-panel[data-active-card-style="..."]`, switchable live from Settings, so Isaac can compare them against his own real docs. `tint` (reuses the mark's own hue-agnostic `filter: saturate()/brightness()` hover trick, so the active card reads as "the same visual language as the highlighted text" rather than a bolted-on effect) is the current default; `ring` is kept as the "old" option rather than deleted.
- **Experimental settings**: a new Settings section (`#active-card-style-select` today, more can be added the same way) for trying UI treatments live against real content instead of guessing from screenshots — `config.experimental` in `storage.js` (new, backwards-compatible optional field, merged the same way as `gemini`/`claude`). Deliberately styled distinctly (dashed section divider, monospace label) to read as scratch space, not a real setting — the plan is to fold a choice into the real default and drop the toggle once it sticks, not let this section accumulate forever.
- **Style-guide prompt wording**: both `review.js` and `generative.js` reframed the injected style-guide block from "The author's target voice and style: ..." to "The user adds this detail to help you understand the target style: ..." — makes explicit to the model that this is supplementary context supplied by the person, not a claim about the document's actual current voice.
- **Global "summon a review" hotkey**: Cmd/Ctrl+/ focuses (and selects the contents of) the custom-instruction input from anywhere, including while the editor's contenteditable has focus — added to the same `window` keydown handler as the existing Escape/Alt+Up-Down/Cmd+K shortcuts. Running it (Enter, or Cmd/Ctrl+Enter) needed no new code: the existing `customInstructionInput` keydown handler checks only `e.key === "Enter"`, which is true regardless of whether a modifier is also held, so both were already covered — confirmed with Playwright rather than assumed.
- **Escape pops back to the editor**: the round-trip's other half — Cmd/Ctrl+/ gets you into the review panel, but there was no quick way back out. Escape's handler now only closes modals when one's actually open; otherwise, if `document.activeElement` is inside `#review-panel` (the ask box, a pass chip, a finding card reached via arrow-nav, ...), it calls `editor.commands.focus()` and returns. No explicit position snapshot/restore needed — ProseMirror keeps `state.selection` alive across a DOM blur on its own, so refocusing lands you back exactly where you were writing, as long as nothing else moved the selection in the meantime (clicking a *card* deliberately does move it, via `focusFinding`, so Escape from a card returns you to the finding's location instead — that's correct, since you explicitly navigated there).
- **API key fields aren't `type="password"` anymore**: Isaac noticed Chrome kept offering to save a password while typing in the unrelated custom-instruction input. Root cause: Chrome's save-password heuristic scans the whole DOM for *any* `<input type="password">` (even one sitting in a currently-`hidden` modal elsewhere on the page), and `autocomplete="off"` doesn't suppress it — Chrome deliberately ignores that attribute on password fields so sites can't disable the password manager. The two `.api-key-input` fields (Settings → LLM connection) are now `type="text"` with `-webkit-text-security: disc` (a long-supported, if non-standard, Blink/WebKit CSS property) for the same dot-masked look, plus an explicit `.key-toggle-btn` ("Show"/"Hide") since there's no more native reveal behavior to lean on. Root-cause fix, not a workaround — there is now no `input[type="password"]` anywhere in the DOM, so the browser has nothing to offer to save, confirmed via Playwright (`input[type="password"]` count is 0 on the fully-loaded page). Caveat: `-webkit-text-security` isn't supported in Firefox, where the field would just render unmasked — an accepted tradeoff since this is a Chrome-specific annoyance being fixed for a Chrome-based workflow.

- **Editing under a flag clears it** — implemented as a real ProseMirror plugin (`ReviewFlag.addProseMirrorPlugins`, `editor.js`), not app-level `onUpdate` logic, specifically so the mark removal merges into the *same* transaction batch as the edit that caused it — undoing the edit restores the text and the flag together as one step, not two. "Touched" is decided by content, not position: on every doc-changing transaction, each existing flag's old range is mapped forward through a real `Mapping` (combining every transaction in the batch), and the text at the old range is compared against the text at the mapped new range — different text clears the flag, identical text (the edit happened elsewhere and just shifted this range) leaves it alone. A useful side effect of comparing *content* rather than just "was this range touched": toggling bold/italic on flagged text does **not** clear the flag, since the characters themselves didn't change — only an actual insertion/deletion/replacement does. No storage-schema change at all (see the localStorage compatibility policy above) — this only changes what happens the *next time* an already-saved flagged doc gets edited, not the shape of anything on disk.
- **Sidebar live-refresh, a real gap this surfaced**: the findings sidebar used to only re-render after its own explicit button clicks (accept/dismiss/run/dismiss-all) — a mark disappearing for any *other* reason (this new auto-dismiss-on-edit behavior, but the same gap would've applied to anything else that touches marks outside those buttons) left a stale card sitting in an open panel. Fixed at the root instead of patching each call site: `syncUI()` now calls `renderFindings()` whenever the review panel is visible, and since every mark-changing action already dispatches a real transaction (which triggers `onUpdate` → `syncUI` synchronously before the dispatching call even returns), the explicit `renderFindings()` calls after accept/dismiss/dismiss-all/run-a-pass were redundant and removed. `findingsListEl`/`dismissAllBtn` had to move into the pre-`createEditor()` TDZ-safe block (same trap as `toolbar` and `reviewScopeNote` before them) since `syncUI` can call `renderFindings()` synchronously during construction.
